# Adapter Guide

`vrm-rs` does not require Bevy, wgpu, ash, or any specific engine.

Engines integrate by implementing traits from `vrm-adapter`:

- `SceneGraph`: parent/child traversal. Use `visit_children` for hot traversal paths that should avoid allocating a fresh child `Vec`.
- `TransformAccess`: transform reads/writes.
- `WorldTransformAccess` / `WorldMatrixAccess` / `WorldTransformUpdate`: world transform reads, exact world matrix reads for parity collider offsets, and explicit synchronization before parity spring simulation.
- `MorphTargetAccess`: expression morph target application.
- `MaterialAccess`: material color, texture transform, and HDR emissive intensity application.
- `MtoonPipelineAccess`: MToon base/outline pipeline pass selection.
- `TextureResolver`: texture handle lookup.
- `AnimationSink`: consume runtime events.

Engines that want humanoid pose parity can capture a `HumanoidPoseRig` from their scene graph. It provides raw absolute/rest-relative pose access, normalized absolute/rest-relative pose storage, and normalized-to-raw writeback through transform traits.

Engines that want a single orchestration point can use `VrmRuntimeDriver`. It applies animation frames, runtime expression events, node constraints, spring bone, first-person visibility, one-shot VRM0 root orientation compatibility, MToon pipeline hints, and effective emissive strength writeback through the traits above.

Engines that do not use Bevy can start from `HeadlessSceneState` in `vrm-adapter`. It is a renderer-neutral staging scene that implements scene graph, local/world transforms, world matrix access, constraint rest capture, morph weights, material color/texture/emissive writes, MToon pipeline pass writes, visibility, and lookAt rotation storage. A wgpu, ash, or custom engine can either use it directly as the runtime-driver staging layer or mirror its small map-based design with engine-native handles.

If the engine is loading through the facade crate, `vrm_rs::headless_scene_from_loaded` builds that staging scene from `LoadedVrm::scene`, and `vrm_rs::evaluated_world_matrices` runs the same renderer-independent zero-delta runtime path used by the render-parity captures before returning world matrices. This is the shortest path for full-scratch wgpu/ash integrations that want validated VRM runtime ordering without adopting the Bevy adapter.

Renderer diagnostics and render-parity adapters should make clip-space policy explicit instead of baking it into ad hoc formulas. `vrm-adapter` exposes `ClipDepthMapping` marker types (`ZeroToOneDepth`, `ReverseZeroToOneDepth`, `NegativeOneToOneDepth`), `RendererFrontFace` for y-down screen-area winding checks, and `project_triangle_to_screen::<DepthPolicy>` for renderer-neutral screen bounds, signed area, normalized depth, and WebGL-reference depth. The capture examples use `project_triangle_to_screen::<ZeroToOneDepth>` for wgpu and `project_triangle_to_screen::<ReverseZeroToOneDepth>` for Bevy, then compare both against three-vrm in the same reference depth convention.

Coordinate-system policy is also type-level instead of a renderer-global mutable setting. `CoordinateSpaceMapping` converts VRM/glTF positions, directions, rotations, `Transform`s, and affine transform matrices into a target engine space. The built-in marker types are `VrmCoordinateSpace` / `GltfCoordinateSpace` for the native right-handed Y-up VRM convention and `FlipZCoordinateSpace` / `LeftHandedZForwardCoordinateSpace` for engines that mirror Z into a left-handed Y-up world. Projection helpers such as `project_vrm_triangle_to_screen::<CoordinateSpace, DepthPolicy>` compose the coordinate-space policy with the clip-depth policy, so a full-scratch wgpu/ash engine can make axis mapping, depth mapping, and winding policy explicit at the call site. The matrix helpers are intentionally named `from_vrm_affine_matrix` / `to_vrm_affine_matrix`; projection or other projective matrices should use the projection helpers instead of affine basis remapping.

When an engine stores transforms in a non-VRM coordinate space, wrap the engine adapter at the runtime boundary with `coordinate_space_target::<CoordinateSpace, _>(&mut engine_state)`. The `CoordinateSpaceTarget` wrapper delegates scene graph, morph, material, visibility, texture, and MToon calls unchanged, while converting local/world transforms, world matrices, constraint rest rotations, and lookAt rotations between VRM space and the engine space. This keeps `vrm-core` and `vrm-runtime` Sans I/O and VRM-native, while engine integrations choose the coordinate policy through generics.

For spring bone parity with three-vrm, capture `SpringRestMap` once after the engine scene has its initial local/world transforms, then create a `CenterSpringRuntimeState` with `SpringRestMap::runtime_state`. Pass both to `VrmRuntimeDriver::tick_with_spring_parity` or call `step_spring_bone_system_parity` directly. This path keeps particle tails in center space, uses each selected child's local translation like three-vrm's `child.position`, selects the next spring joint only when it is the direct child before falling back to the first scene child, uses `WorldMatrixAccess` for collider offset materialization, and preserves the VRM0 7cm final-joint fallback. `tick_with_spring_parity` requires `WorldTransformUpdate` and synchronizes world transforms after animation/constraint writes and before spring simulation. The older `SpringRuntimeState` and `tick` remain available as a simpler world-space stepping path.

First-person `auto` annotations use `SceneGraph` plus the humanoid head bone to hide head descendants in first-person view while keeping them visible in third-person view. Engines that expose skinned mesh indices, skin weights, and skeleton joints can also implement `FirstPersonMeshAccess` and use the headless mesh planning helpers to clone first-person meshes with head-weighted triangles removed.

The root `examples/headless_vrma_animation.rs` file demonstrates the renderer-neutral animation path: it loads a VRM avatar and separate VRMA clip, samples `VrmAnimation` frames, applies them through `HumanoidPoseRig` and `HeadlessSceneState`, and prints hips/head/lookAt/expression state without depending on Bevy, wgpu, ash, or committed binary fixtures. The root `examples/custom_engine_adapter.rs` file demonstrates a full-scratch engine flow without Bevy, wgpu, or ash: an engine keeps `HeadlessSceneState` as its staging scene, runs `VrmRuntimeDriver`, then copies local transforms, morph weights, material color writes, emissive intensity, first-person visibility, constraints, and MToon pipeline passes back into engine-owned node/material tables. The root `examples/mtoon_renderer_skeletons.rs` file demonstrates renderer-owned MToon materialization for wgpu-like and ash-like engines without adding either renderer as a dependency. It starts from `mtoon_renderer_material_plans`, then maps `MtoonRendererMaterialPlan`, `RendererMaterialPipelinePlan`, `MaterialRef`, `TextureRef`, `MtoonTextureSlot`, and `MtoonSamplerHint` into engine-owned pipeline descriptors, pass ordering, alpha/depth/cull state, render order, texture/sampler slots, uniform layout sizing, and material tables, leaving actual shader modules, descriptor sets, bind groups, and render pass construction in downstream renderer code. Renderers that want a stable packed GPU surface can use `MtoonGpuMaterial` / `MtoonGpuUniform`, the `mtoon_gpu_*_binding_number` helpers, and `MTOON_REFERENCE_WGSL`; this keeps MToon parameter packing, emissive strength application, debug/pass flags, and texture/sampler binding policy shared while backend shader modules remain renderer-owned. `examples/wgpu_mtoon_pipeline_materialization.rs` is the more concrete wgpu-shaped version: it maps the same public plan into render-pipeline keys, primitive/depth/blend state, WGSL module and entry-point names, bind-group layout entries, texture and sampler binding pairs, sample-type choices, shared uniform payloads, and a sorted material table that a `wgpu` backend can replace with real `wgpu::RenderPipelineDescriptor`, `wgpu::BindGroupLayoutEntry`, `wgpu::SamplerDescriptor`, and bind-group writes at the renderer edge. `examples/ash_mtoon_pipeline_materialization.rs` is the concrete Vulkan-shaped version: it maps the same public plan into descriptor-set layout bindings, combined image sampler writes, push constants, rasterization/depth/blend state, pass-specific shader module names, shared uniform buffers, and a sorted draw queue that an `ash::vk` backend can replace with real Vulkan create-info values at the edge. Engines loading glTF material data can apply `GltfMaterialPipelineOverride` to the same plan at their IO edge for alpha-mode, cutoff, and double-sided policy without depending on `vrm-io`. The root `examples/bevy_mtoon_materialization.rs` file demonstrates the Bevy-facing version: `BevyMtoonMaterialPlan` is copied into an engine-owned Bevy `Asset`, carries the same shared GPU uniform for custom materials, and runtime `BevyVrmMaterialState` is applied through `VrmBevyMaterialAsset` without requiring `vrm-rs` to define a shader or concrete render material.

For Bevy, `vrm-adapter-bevy` starts with a 0.19.0 registry/descriptor/runtime skeleton. `BevyNodeMap` maps `NodeRef` to entities, `BevyRuntimeSceneState` is a lightweight `Entity` keyed scene state implementing the transform, world-transform, scene-graph, visibility, constraint-rest, morph target, material, and MToon pipeline traits, `bevy_mtoon_descriptors` bridges renderer-agnostic MToon descriptors, `bevy_mtoon_material_plans` converts those descriptors into Bevy-facing material plans with pass kind, render order, alpha/cull/depth state, colors, emissive intensity, cutoff, texture references, and outline width, and `VrmRuntimePlugin` installs `BevyVrmRuntimeConfig`, `BevyVrmDocument`, `BevyVrmRuntimeEvents`, `BevyVrmRuntimeState`, `BevyVrmSpringParityState`, `BevyVrmSpringParityRecapture`, `BevyVrmRuntimeError`, a `BevyRuntimeSceneState` resource, a runtime tick system, and lightweight ECS writeback systems. The Bevy scene state can run both `VrmRuntimeDriver::tick` and the three-vrm parity-oriented `tick_with_spring_parity` path after a `SpringRestMap` capture. The plugin tick reads `BevyVrmDocument`, `BevyVrmRuntimeEvents`, and `BevyVrmRuntimeConfig`, preserves one-shot VRM0 orientation state in `BevyVrmRuntimeState`, consumes `BevyVrmSpringParityState` when available, and records the last adapter error text in `BevyVrmRuntimeError`. The plugin writeback systems copy runtime output into `Transform`, `BevyVrmVisibility`, `BevyVrmMorphWeights`, and `BevyVrmMaterialState` components keyed by `VrmNode` and `VrmMaterialBinding`. When an app wants to seed or refresh the adapter scene from ECS before running the driver, schedule `read_bevy_transforms_into_scene_state` before `tick_scene_state_runtime`; it copies `Transform` and optional `BevyVrmVisibility` components into `BevyRuntimeSceneState` without being auto-registered by the plugin. For spring parity, schedule `initialize_spring_parity_state` after readback and before `tick_scene_state_runtime`; request recapture through `BevyVrmSpringParityRecapture` when the model, rest pose, spring setup, or manual reset state changes. Optional Bevy asset writeback hooks cover material assets (`VrmBevyMaterialAsset`), morph target assets (`VrmBevyMorphTargetAsset`), and first-person headless mesh assets (`VrmBevyFirstPersonMeshAsset`) while keeping concrete renderer policy outside core crates.

The optional `vrm-adapter-bevy/render` feature adds a practical scene bridge for apps that want Bevy-owned `Mesh3d`, `StandardMaterial`, and `Image` assets. `spawn_vrm_scene` consumes a `LoadedVrm`, builds a `BevyVrmInstance` component, creates textured Bevy primitives, and CPU-bakes skinning plus morph targets into mesh assets each update through `BevyVrmScenePlugin`. A separate `.vrma` file can be attached as `BevyVrmAnimationClip`; the update system samples the clip, applies it through `HumanoidPoseRig` and `HeadlessSceneState`, then refreshes the Bevy meshes. This is intentionally an integration layer over the Sans I/O runtime rather than a replacement for Bevy's asset server. The `viewer` feature also exposes `VrmOrbitCamera` and `BevyVrmOrbitCameraPlugin` for left-drag orbit, right/middle-drag pan, wheel zoom, `F` focus, and `R` reset. The root `examples/bevy_vrma_viewer.rs` demonstrates the flow, and `just bevy-vrma-viewer` runs it with `cargo run --release` against local external fixtures.
For Bevy render-parity and custom-material integrations, `BevyOwnerSampleOverrideRecord`, `bevy_owner_sample_override_buffer_plans`, `bevy_owner_sample_override_buffer_plan_for_surfaces`, and `bevy_owner_sample_override_buffer_plan_for_surfaces_and_draw` convert `RenderOwnerSampleSelectionPlan` values into packed records suitable for a Bevy `ShaderStorageBuffer` at `RENDER_OWNER_SAMPLE_OVERRIDE_BINDING`. Prefer the draw-aware helper when manifest entries carry `sample_geometry`: it filters by `RenderOwnerSampleDrawKey` (`node`, `mesh`, `primitive`, `pass`) before building the buffer, preventing same-material/same-triangle decisions from leaking into another draw. The headless capture example binds that buffer into `BevyMtoonMaterial` so the WGSL shader can consume owner/sample decisions before fragment output.

For apps that want a concrete renderer path without Bevy, `crates/vrm-adapter-wgpu` provides a wgpu/winit viewer over the same IO and Sans I/O runtime layers. It exposes `WgpuVrmViewerOptions` and `run_vrma_viewer`, loads a `.vrm` plus optional `.vrma`, samples animation through `HumanoidPoseRig` and `HeadlessSceneState`, CPU-bakes skinning and morph targets into wgpu buffers, uploads glTF base-color textures, and exposes the same orbit/pan/zoom/focus/reset camera workflow. It also exposes `wgpu_mtoon_resource_plans` for renderer owners that need MToon pass state, `wgpu` buffer usage, shader-stage visibility, sample types, sampler policy, shared uniform bytes, and reference WGSL without opening a window. `wgpu_owner_sample_override_buffer_plans` converts a `RenderOwnerSampleSelectionPlan` into per-surface read-only storage-buffer plans with a stable `WgpuOwnerSampleOverrideRecord` ABI, and `wgpu_owner_sample_override_buffer_plan_for_surfaces_and_draw` applies the same concrete draw-key filtering as the Bevy helper. `wgpu_owner_sample_override_bind_group_layout_entry` exposes the matching fragment storage-buffer layout entry at `RENDER_OWNER_SAMPLE_OVERRIDE_BINDING`, so downstream wgpu shaders can consume the same owner/sample decisions before readback rather than only patching final RGBA bytes. `just wgpu-vrma-viewer` runs the crate-local `vrma_viewer` example with `cargo run --release -p vrm-adapter-wgpu --example vrma_viewer` against repo-relative external fixture paths.

Browser/WASM viewer samples live under `examples/wasm/`. `examples/wasm/bevy-web` starts a Bevy 0.19 WebGPU canvas and uses `vrm-adapter-bevy/render` plus `spawn_vrm_scene`; `examples/wasm/wgpu-web` uses the Bevy-independent `vrm-adapter-wgpu::WgpuCanvasViewer` entrypoint over `wgpu::SurfaceTarget::Canvas`. Both samples accept local `.vrm` and optional `.vrma` files through the browser file picker, so official or third-party binary fixtures stay outside the repository. Use `just wasm-web-check` for a wasm32 compile check, or `just wasm-bevy-web-build` / `just wasm-wgpu-web-build` to run release `wasm-pack build --target web` in the sample directories.

For Vulkan apps, `crates/vrm-adapter-ash` provides the analogous ash-shaped boundary without creating a swapchain or presentation surface. `AshVrmFramePlanner` loads/evaluates a VRM plus optional VRMA clip through the same Sans I/O runtime, then emits CPU-baked `AshVrmPrimitive` vertex/index data including normal/tangent attributes, `AshTextureUpload` RGBA uploads with `ash::vk::Format`/`Extent3D`, material records, a frame-level `AshSceneUniform`, and `AshMtoonPipelinePlan` values using `ash::vk` topology, cull, depth, blend, descriptor, sampler, shader-stage enums, the shared `MtoonGpuUniform`, plus packed `AshMaterialUvUniform` and `AshMaterialExtraUniform` payloads derived from `LoadedVrm::material_uv_transforms` and `LoadedVrm::material_shading_plan`. `AshSceneOptions` controls the parity camera, light color/scale, MToon lighting config, aspect ratio, and Vulkan clip-space Y flip used by the scene uniform and screen-coordinate outline expansion; the current offscreen parity path keeps CCW front-face classification with that Y flip, matching the wgpu/Bevy capture contract for generated outline and base-color diagnostics. `AshVrmFramePlanOptions` exposes matching CLI knobs for renderer experiments. Texture uploads are derived from the full set of MToon descriptor TextureRefs plus base-color material records, so downstream renderers can allocate every sampled image required by the MToon binding plan rather than only the visible base slot. Descriptor sets expose stable binding numbers for all MToon texture slots and the material, scene, UV-transform, and render-extra uniform buffers, with missing textures resolved to the example renderer's fallback textures; texture bindings carry `AshSamplerPlan` values derived from the source glTF sampler filter, wrap, mipmap, and LOD policy while preserving MToon normal-map decode intent. Shader authors can use `ash_mtoon_uniform_binding`, `ash_mtoon_scene_binding`, `ash_mtoon_uv_uniform_binding`, `ash_mtoon_render_extra_binding`, and `ash_mtoon_texture_binding` as the legacy combined-sampler GLSL binding contract, or the separate texture/sampler binding helpers for the preferred WGSL ABI. `ash_owner_sample_override_buffer_plans` converts the same `RenderOwnerSampleSelectionPlan` into per-surface `STORAGE_BUFFER | TRANSFER_DST` upload plans with `vk::DescriptorType::STORAGE_BUFFER`, fragment-stage visibility, and a stable `AshOwnerSampleOverrideRecord` ABI; `ash_owner_sample_override_descriptor_set_layout_binding` exposes the matching `vk::DescriptorSetLayoutBinding`. `just ash-vrma-frame-plan` runs the crate-local `frame_plan` example in release mode and prints the generated plan counts. `ash_renderer_frame_from_plan` is the renderer-edge helper: it turns the frame plan into vertex/index buffer uploads, sampled-image resource plans, per-pipeline material/UV/render-extra uniform uploads, a shared scene/camera/light uniform upload, concrete `AshGraphicsPipelinePlan` values with vertex layout/color/depth formats, resolved descriptor-set bindings, and sorted draw calls. `AshRendererFrame::resource_manifest` and `ash_renderer_resource_manifest` classify frame resources for renderer-owned caches: textures, samplers, descriptor-set layouts, and graphics pipelines are marked persistent for a stable asset/shader/render-target setup, while CPU-baked vertex/index buffers, uniforms, owner/sample storage buffers, and descriptor-set writes are marked frame-dynamic. `crates/vrm-adapter-ash/examples/renderer_integration.rs` shows a mock ash renderer consuming those plans and the manifest while allocating buffer/image/sampler/pipeline/descriptor handles without using unsafe Vulkan calls; `just ash-renderer-integration` runs that example. `crates/vrm-adapter-ash/examples/unsafe_device_renderer.rs` is the real ash device materialization example: it loads `Entry`, creates an instance/device/graphics queue family, allocates real `vk::Buffer`/`vk::DeviceMemory`, `vk::Image`/`vk::ImageView`, host uniform buffers for the shared MToon ABI, scene uniform, UV-transform uniform, and render-extra uniform, mip-chain texture staging buffers, samplers, descriptor set layouts/pool/sets, combined-image-sampler or separate texture/sampler descriptor writes with fallback textures, pipeline layouts, an offscreen color/depth render pass and framebuffer, embedded minimal shader modules, graphics pipelines, a primary command buffer that uploads all texture mip levels, records sorted indexed draws, and an optional queue-submit/readback path that copies the color attachment to a host buffer. Pass `--vertex-spv` and `--fragment-spv` to replace the built-in color-only smoke shader with precompiled SPIR-V that matches the emitted vertex input and descriptor-set layout; the example validates SPIR-V alignment/magic and records the shader source kind in its `.rgba.json` artifact. `crates/vrm-adapter-ash/shaders/mtoon_base.wgsl` is the preferred source-controlled MToon handoff shader; `just ash-mtoon-base-readback` compiles it through Naga with `--no-adjust-coordinate-space` because Ash scene matrices are already Vulkan-clip-space adjusted, then runs it through the external-SPIR-V path with the separate texture/sampler descriptor model. `crates/vrm-adapter-ash/shaders/mtoon_base.{vert,frag}.glsl` and `just ash-mtoon-glsl-base-readback` remain only as a legacy combined-sampler comparison lane. The readback path can also write render-parity `.rgba.json` and direct `.imqraw` artifacts, so an ash backend can join the same raw-image verification language as the wgpu and Bevy captures; `just render-parity-samples-ash-gated` gates the current six-fixture sample sweep with Ash included. `just ash-unsafe-device-renderer` runs the checksum smoke when a Vulkan loader and physical device are available; `just ash-render-parity-readback` additionally writes and verifies the readback artifacts under `.external-fixtures/ash-readback-smoke/`; local CI checks the release-built `--help` path. For custom wgpu/ash engines, keep renderer resources outside `vrm-rs` and use `MaterialRef`/`TextureRef` as stable lookup keys into engine-owned tables.
Ash renderer owners that already build an `AshRendererFrame` can call `ash_renderer_frame_from_plan_with_owner_sample_selection` to carry `RenderOwnerSampleSelectionPlan` decisions into the frame as per-pipeline `OwnerSampleOverride` storage buffers. The unsafe device example includes the matching descriptor-pool and descriptor-write path for uniform buffers, storage buffers, Vulkan combined image samplers, and WGSL-compatible separate sampled-image/sampler descriptors, so downstream Vulkan code can consume the same owner/sample correction data before fragment output instead of only patching readback RGBA bytes. `AshRendererFrame::resource_manifest()` is the renderer-facing cache contract: `handle_lifetime` tells an engine whether the Vulkan handle can be cached across animation frames for the same asset/shader/render target shape, while `lifetime` tells whether the contents or descriptor writes are still frame-dynamic. In practice, buffers, uniforms, descriptor sets, textures, samplers, descriptor-set layouts, and pipelines all expose persistent handles; buffer bytes, uniform bytes, and descriptor writes remain frame-dynamic and must be refreshed after the relevant in-flight fence. `ash_mtoon_renderer_cache_keys` turns the same frame plus swapchain extent and `AshMtoonShaderCacheKey` into hashable pipeline/descriptor/sampler/buffer/uniform/texture cache keys for downstream ash renderers; buffer and uniform keys track shape while texture keys include a deterministic payload hash, and `AshMtoonShaderCacheKey::from_spirv_words` lets pipeline caches invalidate when SPIR-V changes even if entry point names stay the same. `ash_descriptor_pool_plan` derives `max_sets` and per-type pool sizes from the frame's descriptor bindings, including separate sampled-image/sampler descriptors and owner/sample storage buffers, so engines can create descriptor pools without copying example-local counting rules. Descriptor-set layout, descriptor-pool, descriptor-set allocation, and pipeline-layout plans also expose closure-scoped create-info helpers, keeping short-lived binding/layout arrays valid while engines still own Vulkan handle creation. `ash_sampler_resource_plans` returns the default-resolved sampler create plans in the same order used by descriptor-write `sampler_index` values, so engines can allocate sampler handles without duplicating descriptor traversal. `ash_descriptor_write_plans` validates the frame's descriptor references and emits renderer-owned write records for uniform buffers, storage buffers, uploaded or fallback textures, separate samplers, and combined image samplers, leaving only real Vulkan handles to the engine. `ASH_FALLBACK_TEXTURES`, `ash_fallback_texture_rgba`, and `ash_fallback_texture_mip_level` define the shared white/black/neutral-normal fallback order and 1x1 RGBA upload payload used by both offscreen and windowed MToon renderers. `ash_texture_mip_upload_bytes` and `ash_texture_upload_command_plan` expose tightly packed mip upload bytes, `vk::BufferImageCopy` regions, the standard `UNDEFINED -> TRANSFER_DST_OPTIMAL -> SHADER_READ_ONLY_OPTIMAL` texture barriers, and `AshTextureUploadCommandSequence` for the barrier/copy/barrier order used by `cmd_pipeline_barrier` plus `cmd_copy_buffer_to_image`, while leaving staging buffers, images, and unsafe command recording in the renderer. `AshColorAttachmentReadbackPlan` similarly exposes `AshColorAttachmentReadbackCommandSequence` for the color-attachment readback barrier and `cmd_copy_image_to_buffer` payload. `ash_graphics_pipeline_state_plan` exposes the shared fixed-function graphics-pipeline state for a frame pipeline: vertex binding/attributes, topology, viewport/scissor, rasterization, depth, and blend policy. `ash_swapchain_surface_plan` exposes the windowed surface policy used by both Ash windowed paths: UNORM format preference, MAILBOX/FIFO present mode, current or clamped extent, image-count capping, pre-transform preservation, supported composite-alpha selection, and required color-attachment usage validation. `ash_classify_swapchain_acquire` and `ash_classify_swapchain_present` centralize the `ERROR_OUT_OF_DATE_KHR` / `SUBOPTIMAL_KHR` recreate policy for engines that own unsafe acquire/present calls. `ash_windowed_submit_plan` and `ash_windowed_present_plan` expose the standard color-attachment wait stage, command buffer, fence, render-finished semaphore, swapchain, and image-index payloads used to build `vk::SubmitInfo` and `vk::PresentInfoKHR`. `ash_drawable_frame_from_renderer_frame_with_options` lowers a renderer frame into transparent-background or opaque-background render-pass clear metadata plus coalesced `AshCommandPlan` values for bind-pipeline, bind-descriptor-set, bind-vertex-buffer, bind-index-buffer, and draw-indexed recording. Both the offscreen unsafe renderer and the windowed swapchain renderer consume those public plans, so pipeline policy, swapchain surface policy, skipped draw validation, and command ordering live in the crate instead of in example-local loops. `AshVrmFramePlanOptions --descriptor-binding-model separate-image-sampler` is now the default and is the preferred shader ABI for Ash: MToon texture/sampler pairs use the same even/odd binding shape as wgpu/WGSL, while Ash-specific scene, UV, render-extra, and owner/sample storage bindings live at non-conflicting higher binding numbers. `combined-image-sampler` remains available for legacy GLSL handoff shaders. `crates/vrm-adapter-ash/examples/windowed_viewer.rs` is the windowed counterpart: it creates a winit window, ash surface, Vulkan swapchain, render pass, depth buffer, synchronization objects, and presents directly to the swapchain. The default path materializes a full `AshRendererFrame` each redraw, samples the optional VRMA clip at elapsed playback time, and draws through WGSL/Naga MToon SPIR-V with separate texture/sampler bindings and `vs_main`/`fs_main` entry points (`just ash-mtoon-wgsl-base-shaders`). The windowed path keeps descriptor-set layouts, pipeline layouts, graphics pipelines, Vulkan samplers, payload-keyed model texture images, 1x1 fallback textures, and swapchain-image draw command buffers persistent at their natural lifetimes, while descriptor pools/sets, shape-keyed vertex/index/storage buffers, and shape-keyed uniform buffers live in per-frame-slot dynamic caches keyed by the public cache-key helpers plus swapchain extent where relevant. Dynamic buffer and uniform bytes are rewritten only for the current waited frame slot, descriptor sets are updated only for that slot, model and fallback texture staging buffers are uploaded once per cache key and destroyed, and swapchain draw command buffers are reset and rerecorded rather than reallocated. `AshWindowedRunValidation`, `AshWindowedResizeValidation`, and `AshMtoonWindowedCacheStats` expose the same startup, resize-recreate, and steady-state cache-hit checks used by the example, so downstream windowed ash apps can keep smoke-test behavior aligned without copying private example code. The MToon path supports `--frames-in-flight` (default `2`) by keeping descriptor sets, vertex/index/storage buffers, and uniform buffers in per-frame-slot dynamic caches; textures, samplers, descriptor-set layouts, pipeline layouts, graphics pipelines, fallback textures, and swapchain-image command buffers remain persistent at their natural lifetime. Pass `--simple-preview` to keep the older CPU-projected position/color mesh preview compiled from `just ash-windowed-simple-shaders`. Use the offscreen `unsafe_device_renderer` example for readback parity artifacts. `just ash-windowed-viewer` compiles local SPIR-V into `target/` and opens the animated window; `just ash-windowed-viewer-smoke` adds `--max-frames` for auto-exiting smoke runs; `just ash-windowed-viewer-cache-smoke` additionally enables `--print-cache-stats --require-cache-hits` so a release-built animated run proves the steady-state caches are being hit.

`AshWindowedFrameSyncPlan::select_acquired_frame` turns an acquired swapchain image into frame slot, swapchain image slot, previous-image fence, suboptimal flag, and next-frame index data. `AshWindowedFrameSyncSelection` can then build submit and present payload plans from engine-owned synchronization handles, and `AshWindowedSubmitInfoPlan` / `AshWindowedPresentInfoPlan` own the small arrays needed to build `vk::SubmitInfo` and `vk::PresentInfoKHR`. Downstream windowed Ash renderers can reuse the same frame-sync policy while keeping `vk::Fence` waits, acquire, queue submit, and present calls at their own unsafe Vulkan edge.
`AshRenderPassCreationPlan::with_render_pass_create_info` covers the render-pass create-info envelope shared by offscreen readback and windowed swapchain rendering: color/depth attachment descriptions, attachment references, subpass wiring, target-specific final layout, and dependency policy stay in crate-owned data while engines still create and destroy their own `vk::RenderPass` handles.
`AshCommandBufferBeginPlan` and `AshRenderPassBeginPlan` cover the remaining command-recording envelope used around the shared `AshCommandPlan` stream. Engines pass their own `vk::RenderPass` and `vk::Framebuffer` handles, while `vrm-adapter-ash` supplies the reusable/one-time command-buffer flags, render area, and clear-value ordering derived from `AshRenderPassPlan`.
`AshCommandPoolPlan` and `AshSemaphorePlan` cover the shared command-pool and binary-semaphore create-info used by the offscreen renderer, windowed MToon renderer, and simple-preview viewer. The helper keeps the resettable-command-pool policy and default binary semaphore creation in crate-owned data while engines still create, reset, destroy, and synchronize the Vulkan handles themselves.
`AshBufferResourcePlan`, `AshHostBufferPlan`, `AshImageResourcePlan`, `AshImageViewPlan`, `AshMemoryAllocationPlan`, `AshFramebufferPlan::framebuffer_create_info`, and `AshSamplerPlan::sampler_create_info` cover the shared host-buffer, 2D image/image-view, memory-allocation, framebuffer, and sampler create-info used by the offscreen and windowed renderers. The helpers expose size clamping, generic host-visible buffer usage, transfer-destination staging policy for MToon uploads, memory-property requirements, allocation size/type handoff, mip-level clamping, optimal 2D image layout, swapchain/owned-image view subresource ranges, framebuffer extent/layer policy, and sampler address/filter/LOD policy while keeping Vulkan memory allocation, binding, mapping, image/view/framebuffer creation, and destruction in the renderer.
`AshCommandBufferAllocationPlan`, `AshFencePlan`, and `AshQueueSubmitPlan` cover the small allocation/synchronization payloads shared by offscreen readback and windowed one-shot upload paths. Engines still allocate command buffers, create/destroy fences, submit queues, and wait on fences themselves, but the primary-command-buffer count/level, signaled vs unsignaled fence flags, command-buffer submit list, and wait-fence list are now crate-owned data.
`AshColorAttachmentReadbackPlan` covers the offscreen parity readback transition: it supplies the `COLOR_ATTACHMENT_OPTIMAL -> TRANSFER_SRC_OPTIMAL` barrier, stage masks, and tightly packed image-to-buffer copy payload for a rendered color target while leaving the color image, readback buffer, queue submission, and host mapping to the renderer.
Ash descriptor writes and draw commands also expose checked handle-resolution helpers for downstream renderers. `AshDescriptorWritePlan::vk_descriptor_set`, `AshDescriptorWritePlan::resolve_write_data`, `AshDescriptorWriteResource::{uniform_resource,storage_buffer_resource,sampler,image_resource,resolve_image_view}`, and `AshDescriptorImageResource::{texture_upload_resource,fallback,resolve_resource}` resolve descriptor-set, buffer, sampler, uploaded-image, and fallback-image inputs without taking ownership of Vulkan handles. `AshDescriptorWriteData` plus `AshDescriptorWritePlan::with_write_descriptor_set` then builds the closure-scoped `vk::WriteDescriptorSet` envelope for uniform/storage buffers, combined image samplers, separate sampled images, and separate samplers, keeping the short-lived Vulkan info arrays valid while engines still own the actual handles and unsafe `update_descriptor_sets` call. `AshCommandPlan::{vk_graphics_pipeline,vk_pipeline_layout,vk_descriptor_set,vertex_buffer_resource,index_buffer_resource,draw_indexed_args,resolve_record_command}` performs the matching command-recording precondition checks before an engine issues unsafe Vulkan `cmd_*` calls. `AshCommandRecordResources` and `AshCommandRecordHandleAccess` let an engine provide pipeline/layout/descriptor/buffer handle tables once per command, and `AshResolvedCommand` returns the typed bind/draw payloads (`AshBindGraphicsPipelineCommand`, `AshBindDescriptorSetCommand`, `AshBindVertexBufferCommand`, `AshBindIndexBufferCommand`, `AshDrawIndexedCommand`) expected by the command stream.

Depth and memory selection are also exposed as data-level helpers. `ash_depth_format_candidates` and `ash_select_depth_format` centralize the preferred depth attachment format order while leaving physical-device format queries to the engine, and `ash_memory_type_index` resolves a memory type from `vk::PhysicalDeviceMemoryProperties`, type bits, and required property flags before the engine allocates Vulkan memory.

`just ash-windowed-viewer-resize-smoke` requests a programmatic resize during the animated MToon windowed run and requires both a post-request `WindowEvent::Resized` and a renderer `recreate_swapchain` call, while still checking steady-state cache hits after the resize path has been exercised.

For shader-source convergence, `AshMtoonWgslShaderAbi` exposes the source-controlled WGSL ABI contract used by the Ash examples and local smokes: the prelude/source paths, `vs_main` / `fs_main` entry points, default SPIR-V artifact names, separate sampled-image/sampler descriptor model, and the rule that Naga coordinate-space adjustment stays disabled because Ash scene matrices already target Vulkan clip space. `ASH_MTOON_WGSL_RESOURCE_BINDINGS` is the typed resource-binding table for `mtoon_base.wgsl`, covering the expected names, bind group/binding numbers, and uniform-buffer/sampled-image/sampler kinds. `tools/ash/compile-ash-mtoon-wgsl-shaders.rs` is the preferred compiler entrypoint for that ABI: it reads `AshMtoonWgslShaderAbi`, validates Naga entry-point and resource-binding reflection against `ASH_MTOON_WGSL_RESOURCE_BINDINGS`, compiles both vertex and fragment entry points through Naga, and writes the canonical SPIR-V artifact names into `--out-dir`. `just ash-mtoon-naga-probe` checks whether the shared `MTOON_REFERENCE_WGSL` helpers can be compiled into Vulkan SPIR-V with naga, and `just ash-mtoon-base-readback` now goes further by compiling the source-controlled Ash WGSL base shader through the ABI script, passing `--vertex-entry vs_main --fragment-entry fs_main`, using the separate descriptor model, submitting the real Vulkan offscreen draw, and verifying the raw `.imqraw` artifact. Use `just ash-mtoon-glsl-base-readback` only when explicitly checking the legacy combined-sampler GLSL path.
`AshShaderModulePlan` and `AshGraphicsShaderStagesPlan` cover the remaining shader handoff create-info: renderers pass their own SPIR-V words, shader module handles, and entry-point `CStr`s, while `vrm-adapter-ash` supplies the `vk::ShaderModuleCreateInfo` and vertex/fragment `vk::PipelineShaderStageCreateInfo` ordering used consistently by the offscreen, windowed MToon, and simple-preview paths. `AshEmptyPipelineLayoutPlan` exposes the descriptor-less `vk::PipelineLayoutCreateInfo` used by simple-preview and downstream debug/minimal passes, while `AshPipelineLayoutPlan` remains the checked descriptor-set-layout path for MToon. `ash_position_color_pipeline_state_plan` exposes the same position/color vertex layout, viewport/scissor, alpha blend, cull, and depth policy used by the simple-preview pass. `AshGraphicsPipelineCreateInfoPlan` then combines shader stages, shared fixed-function state, checked pipeline-layout selection, render pass, and subpass into a closure-scoped `vk::GraphicsPipelineCreateInfo`; offscreen, windowed MToon, and simple/debug renderers can now share the same graphics-pipeline envelope while engines still own `create_graphics_pipelines` and all Vulkan handles.
